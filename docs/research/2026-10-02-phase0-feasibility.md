## guidepup

Out of the box, Guidepup's NVDA API does not meet the speech-capture criteria. It records no timestamps, does not surface cancel events, and only keeps speech that arrives inside a command's capture window. The default capture mode ("initial") keeps only the first speak message after each command. Each captured command is also preceded by an injected Control key that cancels any queued speech, which breaks K7. Underneath, though, Guidepup uses NVDA's built-in Remote Access relay (TLS on 127.0.0.1:6837, channel "guidepup"). NVDA 2026.2 sends that relay every speech sequence at the moment it is queued (with its priority), plus every global cancelSpeech, to every connected leader. So a small Apache-2.0 client written by the harness, joined as a second leader, can capture all speech and global cancels with receipt timestamps. It needs no NVDA code and no GPL add-on. The add-on would only matter for cancellations NVDA makes inside its speech manager, which never reach the relay. This changes the M0-M2 plan: test the relay tap first, and treat the add-on as a later fallback. Provisioning has also changed. guidepup/setup-action was archived on 2026-09-26, its last release (0.21.0) installs NVDA 2026.1.1, and it cannot provision current Guidepup (>=0.29). The supported path is `npx @guidepup/setup@0.29.1 install`, which reads the manifest of the pinned @guidepup/guidepup. Version 0.35.0 maps to the portable NVDA 2026.2 build, pinned by sha256. Keystrokes are real OS-level input: NVDA calls SendInput, and its keyboard hook processes injected keys by default. Guidepup does not care which browser it drives, so a Playwright-launched Chrome for Testing works as long as the harness brings its window to the front. In recent hosted-runner CI on windows-2022/2025, 2 of 100 Chromium test executions needed a retry, both for Playwright teardown errors, not NVDA. Those tests are lenient and configured with retries: 5, though, so they do not show K1-K5 can reach 98%. Licensing is clean: Guidepup and its setup package are MIT. The NVDA binary (GPL-2.0-or-later) is downloaded at CI time and runs as a separate process the harness only talks to over a socket.

### Findings (researcher)

Tag 0.21.0 is lightweight and points to commit acf1a64cc26292ebe0db6a28d1341bd1bae93c65. 4. NVDA forwards each speech sequence to the relay when it is queued for synthesis, before any audio, with its priority. Callback and index commands are stripped out. It also forwards a cancel message on speechCanceled and a pause message on post_speechPaused. The relay sends every message to every authenticated client, so more than one leader can listen. **[critical]**
   - *Evidence (SOURCE, high confidence):* nvaccess/nvda@f62c980:source/_remoteClient/session.py:330-345: registerCallbacks maps speechCanceled to CANCEL and post_speechPaused to PAUSE_SPEECH, and registers pre_speechQueued to sendSpeech. :86-92 and :425-447: BaseCallbackCommand and _CancellableSpeechCommand are filtered out; type=speak is sent with sequence and priority. speech/manager.py:246-248: pre_speechQueued.notify fires at the start of SpeechManager.speak. server.py:458-482 handles newline framing; :577-588 sendToOthers loops over all authenticated clients. FollowerSession keeps callbacks registered while any leader is connected (session.py:357-366, 395-403).
   - *Implication:* The stream holds what NVDA queued to speak, which is the right ground truth for detecting regressions. It does not say what was actually voiced or when audio started: no index or completion markers exist. A queued sequence later dropped or cancelled still appears as a speak message, so speak and cancel messages have to be paired in analysis.
5. Guidepup's public API exposes no timestamps and captures only within command windows. spokenPhraseLog() returns string[] with one joined entry per command. The default capture mode "initial" keeps only the first speak message after the action. capture:true keeps messages until 1 s passes with no speech. Speech outside a command window, such as spontaneous live-region announcements, is never logged. Priority and non-string items in the sequence are thrown away. **[critical]**
   - *Evidence (SOURCE, high confidence):* guidepup@d5c9d80:src/constants.ts:9 sets DEFAULT_CAPTURE="initial". NVDAClient.ts:56 sets SPEAK_DEBOUNCE_TIMEOUT=1000. :206-250: the data handler keeps only string parts, joins them with ", ", and emits 'speak' (ignoring priority). :343-416 processQueue: a SPEAK listener is attached only around action(); in "initial" mode it detaches after the first message (:373-376); the parts are joined with ". " (:401) and pushed to #spokenPhrases, including empty entries. NVDA.ts:846-922 makes lastSpokenPhrase and itemText aliases of the last log entry; :1083-1092 capture() returns {itemText, result, spokenPhrase}; Capture.ts:1-5. The client is a private field (NVDA.ts:47 #client), so a wrapper cannot attach listeners to it. The "initial" truncation was confirmed in issue https://github.com/guidepup/guidepup/issues/115.
   - *Implication:* Taken as-is, Guidepup fails the timestamp and cancel criteria and only partly meets completeness. K1 (an announcement up to 3 s after activation) would pass or fail depending on Guidepup's 1 s debounce, not on NVDA. K4 with "initial" could lose the dialog name if NVDA speaks it in a second sequence. G1 results would measure the adapter's windowing rather than NVDA.
6. In capture mode ("initial" or true), every command first injects a Control keypress (NVDA's stop-speech key). It then waits up to 1 s for a cancel message, plus 250 ms, and repeats while any speech arrives. That actively cancels pending speech and puts extra Control keydown and keyup events into the page. Commands sent with {capture:false} skip all of this and only inject the keys. **[critical]**
   - *Evidence (SOURCE, high confidence):* guidepup@d5c9d80:src/windows/NVDA/NVDAClient.ts:359-360 (if capture, await #stopReading()), :418-451 (sendKeyCode(stopSpeech), race against cancel or 1000 ms, then delay 250 ms), :54-55 (CANCEL_DEBOUNCE_TIMEOUT 250, CANCEL_NOT_FIRE_TIMEOUT 1000), :397-399 (capture false calls action() directly). keyCodeCommands.ts:22-27 maps stopSpeech to the bare Control key. NVDA dedups cancels: speech/speech.py:222-236 skips speechCanceled.notify when beenCanceled is already set, so a stop-speech press with nothing speaking waits out the full 1 s.
   - *Implication:* Capture mode cannot be used for K7 (a queued polite update followed by a focus move) or for any test that depends on the speech queue. The harness should drive NVDA only with perform(cmd,{capture:false}) or its own SendInput, and capture speech separately. It also needs to account for the extra cancel messages that capture mode would cause.
7. Timestamps and full capture are possible without an NVDA add-on. The harness can run its own leader client against the same relay (TLS 127.0.0.1:6837, CA from the build's userConfig, join channel "guidepup"). It would log raw speak (sequence and priority), cancel and pause messages, stamped on receipt with the system precise clock. A cruder alternative is to deep-import lib/windows/NVDA/NVDAClient (the package has no exports map) and wrap NVDAClient.prototype.emit to timestamp 'speak' and 'cancel'. **[critical]**
   - *Evidence (INFERENCE, medium confidence):* Multiple leaders receive broadcasts (nvaccess/nvda@f62c980:_remoteClient/server.py:577-588; session.py:357-366). NVDA's own transport frames messages correctly (transport.py:519-523), so a client with proper newline framing gets complete messages. The published @guidepup/guidepup@0.35.0 tarball has no "exports" field, and lib/windows/NVDA/NVDAClient.js exports the NVDAClient class, which extends EventEmitter and calls this.emit(SPEAK|CANCEL) (NVDAClient.ts:220-249). Latency estimate: in guidepup CI logs (430 commands, runs 36197194587…36832797197), command round-trip including a fixed 250 ms debounce was p50 0.29 s and max 0.38 s. That implies key injection to speech receipt of roughly 10-130 ms (p50 about 40 ms).
   - *Implication:* This may make the GPL add-on unnecessary for M0-M2. The tap meets the per-utterance timestamp criterion (receipt time, about tens of ms after queueing) and makes global cancels visible. The plan should define the Guidepup candidate as Guidepup for provisioning, lifecycle and input, plus this harness-owned tap. Native Guidepup capture should be scored separately, only to document its limits. One M0 run can validate the tap.
8. Cancel visibility at the protocol level is partial. A cancel message exists only for speech.cancelSpeech(), and repeats are suppressed until new speech is queued. That covers keypress gestures, which queue cancelSpeech by default. When focus moves, NVDA silently drops stale focus speech inside the speech manager, and higher-priority speech interrupts lower-priority speech without any cancel message. **[critical]**
   - *Evidence (SOURCE, high confidence):* nvaccess/nvda@f62c980:source/speech/speech.py:222-236 (speechCanceled.notify only in cancelSpeech, guarded by beenCanceled). inputCore.py:587-607 (gestures with SPEECHEFFECT_CANCEL queue speech.cancelSpeech). eventHandler.py:375-395 (doPreGainFocus calls speech._manager.removeCancelledSpeechCommands(), with no notify). eventHandler.py:187-216 (FocusLossCancellableSpeechCommand validity). session.py:86-92 (_CancellableSpeechCommand and callback/index commands are never forwarded).
   - *Implication:* K7 is only partly observable. If the focus move is triggered by an OS-level keypress, the cancel shows up. If the page moves focus by script, NVDA's internal drops or reordering are invisible, both to Guidepup and to the tap. That is exactly the case where a minimal GPL add-on (hooking pre_speechCanceled and SpeechManager removals) or NVDA's speechManager debug log would add information. Keep the add-on as a possible M2 item tied to K7, not an M0 prerequisite.

### Verification (adversarial)

Verdict counts: confirmed 10, partly-true 6

- **PARTLY-TRUE:** In capture mode every command first injects a bare Control press and waits up to 1 s for a cancel plus 250 ms, repeating while speech arrives. This actively cancels pending speech and adds Control keydown/keyup to the page. With capture:false only the keys are sent. A stop-speech press with nothing speaking waits out the full 1 s.
  - *Correction:* The mechanism is right, but the 1 s claim is wrong. speechCanceled is suppressed only while _speechState.beenCanceled is True, and every speak() call resets beenCanceled to False (speech.py:1168). So a Control press after speech has finished naturally still produces a cancel message. The full 1 s timeout happens only when no speech has been queued since the previous cancel. (a) A harness tap automatically receives Guidepup's outbound 'key' messages, which gives free dispatch timestamps on the shared clock. NVDA performs the actual SendInput later, after two wx.CallAfter hops (transport.py:556, localMachine.py:339). (b) Anything the tap sends besides join and protocol_version reaches NVDA's follower and Guidepup, so the tap must stay receive-only. When a leader joins or leaves, NVDA plays wave cues ('controlling', 'disconnected': session.py:217-232, cues.py:35-40) that show up as 'wave' messages, so attach the tap before the segment starts.

It is gated on presentation.reportDynamicContentChanges. The NVDA 2026.2 default UIA.allowInChromium=0 resolves to WHEN_NECESSARY (config/__init__.py:1525-1536), so NVDA uses IA2 for Chrome unless overridden. Two implications: the tap's priority field directly separates K1 (polite) from K2 (assertive), and IA2 is the expected channel for the 'which channel NVDA used' record.
- Every key NVDA processes, including the harness's own activation keys sent through Guidepup or raw SendInput, triggers cancelSpeech by default (keyboardHandler.py:718-737 returns SPEECHEFFECT_CANCEL; inputCore.py:587-607). In K7, a focus move triggered by a keypress mixes up 'cancel caused by the keypress' with 'cancel or drop caused by the focus change'. K7 should use a script-driven focus move after a non-key trigger, or put a known time gap between them.
- Synth configuration and fallback. The build pins synth=oneCore with voice MSTTS_V110_enGB_GeorgeM and keeps NVDAHighlighter on (guidepup/nvda@5dab8e1:overrides/userConfig/nvda.ini:71-85). The silence synth emits no index or done notifications (synthDrivers/silence.py; base supportedNotifications empty, synthDriverHandler.py:101), which changes push and interrupt behaviour and therefore K7 ordering. The relay stream itself does not depend on the synth, because pre_speechQueued fires before synthesis. Record the loaded synth and voice on every run (debugLog.synthDriver at DEBUG level) on windows-2022 and windows-2025.
- nvda.start({capture:false}) turns capture off globally: NVDAClient.#connect stores capture=false, and processQueue checks `options?.capture ?? this.#capture` (NVDAClient.ts:158-179, 359). This is simpler and safer than passing {capture:false} on every call, and guarantees no stop-speech Control presses during AT segments.
- Security note for runs on developer machines rather than CI. NVDA's self-hosted relay binds all IPv4 and IPv6 interfaces by default (server.py:301-302, 324-333). The guidepup build uses the public password 'guidepup' and a private key committed to a public repo. Any host that can reach port 6837 could inject keystrokes while NVDA runs. This is negligible on GitHub-hosted runners but worth a line in the README.

## atdriver

The ARIA-AT "AT Driver" for NVDA works on GitHub-hosted standard Windows runners and is in production use. bocoup/aria-at-gh-actions-helper runs it on windows-2025 (windows-2022 until July 2025), most recently on 2026-09-09 with NVDA 2025.2 and Chrome 151. It is the most proven way to stand NVDA up in CI, and its architecture matches ours: a driver sets page state while input goes through the AT channel. It fails two of the six adapter criteria by design, though. The spec event is only {data: text}, so there are no timestamps. There are also no cancel or interrupt events: spec issue w3c/at-driver#94 is still open, and the NVDA capture synth never overrides cancel(). Capture is an NVDA synth driver ("captureSpeech") that subclasses eSpeak. It forwards only the plain-text strings of each speech sequence and drops index, language, character-mode, break and pitch commands, priority, and utterance grouping. It also reports speech that was later cancelled as if it had been spoken. Key presses do not reach NVDA through its keyboard hook. They are injected inside NVDA (inputCore.manager.emulateGesture, called from the add-on's HTTP thread), and failures are swallowed with HTTP 200. ARIA-AT's own NVDA+Chrome consistency over 5 runs per test ranged from 96.6% to 99.6% across seven 2025 stress reports, so a 98% G1 is plausible for simple canaries but borderline, and consistency is not the same as correctness. Recommendation: reuse the CI recipe (Scream virtual audio, NVDA pinned at 2025.2 or 2025.3.3, ports 8765/5678) and talk to the add-on directly from TypeScript, skipping the Go server. For timestamps and cancel visibility, replace captureSpeech with a fresh ~60-100 line GPL eSpeak-subclass synth that stamps speak() and cancel() with GetSystemTimePreciseAsFileTime. That turns the "AT Driver" candidate and the "minimal add-on" fallback into a single path. Expect 2-4 CI round trips to first captured canary speech with stock components, and 4-7 including the forked synth.

### Findings (researcher)

1. The AT Driver protocol has no per-utterance timestamps and no cancel, interrupt or priority events. Transport is WebSocket; commands are session.new, settings.getSettings/setSettings/getSupportedSettings and interaction.userIntent{name:'pressKeys', keys:[WebDriver code points]}; the only event is interaction.capturedOutput {data: text}. **[critical]**
   - *Evidence (SOURCE, high confidence):* w3c/at-driver@7156eec:schemas/at-driver-local.cddl:77-80 (only field is data: text); index.bs:68,387 (WebSocket transport); index.bs:1182 (the event fires on text 'without speech-specific markup or annotations'); index.bs:1100-1112 (the protocol cannot correlate an intent with its speech, so clients must listen before sending). Issue https://github.com/w3c/at-driver/issues/94 (speech interruptions) is open; in the 2025-09-08 CG minutes timestamps and priority levels were floated but never specified. #90 closed: NVDA and JAWS said correlating input to output is infeasible.
   - *Implication:* The stock adapter fails the timestamp and cancel-visibility criteria outright. K7 (speak/cancel ordering) cannot be measured. Speech can only be timestamped on the harness side at receipt, so the 20 ms skew rule cannot be applied to the speech channel. This triggers the plan's fallback: a minimal GPL add-on, or dropping interruption from scope.
2. Capture is an NVDA synth driver, 'captureSpeech', that subclasses NVDA's built-in eSpeak driver. It is not a speech-module hook and not a SAPI voice. speak() forwards each str element of the SpeechSequence as a separate event and drops every SpeechCommand. cancel() is not overridden. No timestamps are added. A newly connected client is replayed every event since NVDA started. **[critical]**
   - *Evidence (SOURCE, high confidence):* Prime-Access-Consulting/nvda-at-automation@f0caacb:NVDAPlugin/synthDrivers/captureSpeech/__init__.py:6-21 (espeak subclass; 'if not isinstance(speech, str): continue'); speech_socket.py:9-29 (Last-Event-ID handshake, then a loop writing SSE-like text); :38-53 (event = (index, text) with no time). RUNLOG run 34380110982: one capturedOutput per fragment (' Print Page', ' button'), each with a leading space, and the backlog (console window title) replayed right after session.new. The NVDA IO log shows the same sequence carried LangChangeCommand and CancellableSpeech, which were lost.
   - *Implication:* Lost: index, language, character-mode, break, pitch and phoneme commands; Spri priority (which never reaches the synth); speak-call/utterance boundaries; all cancels. It also over-reports speech NVDA queued and then cancelled before it was audible; ARIA-AT saw this as 'double speech' in #94. The plain text is fine for K2-K5 name checks but cannot support K6/K7 judgements about whether something was actually heard.
3. pressKeys is not OS-level input from a separate process and does not reach NVDA through its keyboard hook. The add-on calls inputCore.manager.emulateGesture on its HTTP server thread. Keys bound to an NVDA script run that script directly. Unbound keys are sent with keybd_event inside ignoreInjection(), so NVDA's hook skips them. Exceptions are caught and printed, and the HTTP response is always 200 {}. **[critical]**
   - *Evidence (SOURCE, high confidence):* nvda-at-automation@f0caacb:NVDAPlugin/globalPlugins/CommandSocket/handler.py:54-70 (POST always 200 {}), :79-94 (emulateGesture; except → print only). nvaccess/nvda@release-2025.2:source/inputCore.py:702-716 (emulateGesture → executeGesture, else gesture.send), :549-570 (executeGesture queues speech.cancelSpeech, like a real keypress); source/keyboardHandler.py:656-697 (send() inside ignoreInjection()), :190 (injected keys skipped while ignoreInjected). ## events

An out-of-process B2 listener is feasible. Chromium (ax_dump_events) and NVDA both already use the approach: out-of-context SetWinEventHook plus UIA handlers on an MTA thread. Every web-content MSAA/IA2 WinEvent comes from the Chrome *browser* process, on the per-view Chrome_RenderWidgetHostHWND, with OBJID_CLIENT and child id = -uniqueId. So scoping to the browser process ID (PID) works. The one exception is a document.title change: Windows ignores Chrome's DOCUMENT_TITLE_CHANGED event, and the only WinEvent is the top-level window caption NAMECHANGE, which BrowserUiController delays by a fixed 200 ms coalescing timer. That means the planned title-nonce clock-alignment marker measures pipeline latency rather than clock skew, and would mark nearly every segment INCONCLUSIVE under the 20 ms rule; it needs redesigning before M0 closes. Blink's 150 ms accessibility batching and Chrome's fixed event-firing order also mean B2's ordering for K7 reflects batching, not DOM order. IAccessibleText::get_newText cannot work out of process (it is valid only during the synchronous fire step), so the listener must re-read text. Out-of-process IA2 calls need proxy/stub registration in both processes. Chrome does not provide it, but NVDA's injection does, which would create an NVDA-present/absent asymmetry in B2 unless a BSD-licensed IA2 proxy is registered system-wide first, or B2 resolves only through MSAA and UIA. Chrome's UIA provider has been on by default since M141 and permanently since M151, with no flag to turn it off; IA2 is served at the same time. UIA events are raised only for clients Chrome has seen register, so the listener's UIA subscription has to be verified with a probe. AXMode can be frozen against NVDA and the listener by passing a value, e.g. --force-renderer-accessibility=screen-reader. NVDA's channel is set by nvda.ini [UIA] allowInChromium (default 0 = "only when necessary", which means IA2 when NVDA can inject into Chrome). Pin that setting and confirm the channel from NVDA debug-log markers. I lean slightly towards C#/.NET for B2. Python 3.12 + comtypes is viable but needs mitigations; the main one is that time.time() on Windows has only 15.6 ms resolution before Python 3.13.

### Findings (researcher)

1. Where events come from and how to scope the hook. Chrome raises every web-content MSAA/IA2 WinEvent with NotifyWinEvent(event, legacyHwnd, OBJID_CLIENT, -uniqueId). The call runs on the browser-process UI thread, never in a renderer. legacyHwnd is the per-RenderWidgetHostView child window of class 'Chrome_RenderWidgetHostHWND' (window name 'Chrome Legacy Window'), which is always created. A hook scoped to the browser PID therefore works; a renderer PID would get nothing. The most robust option is a global out-of-context hook per narrow event range, filtering in the callback with GetWindowThreadProcessId(hwnd) == browser PID and the class name. The browser PID can be read from CDP SystemInfo.getProcessInfo (type 'browser'), because Playwright's launch() does not expose the process. Chromium's own external recorder (ax_dump_events) uses the same pattern: SetWinEventHook(EVENT_MIN, EVENT_MAX, .., pid, 0, WINEVENT_OUTOFCONTEXT). **[critical]**
   - *Evidence (SOURCE, high confidence):* chromium/chromium@52fdf83 (trunk 2026-10-01; same code at tag 154.0.8037.92): ui/accessibility/platform/browser_accessibility_manager_win.cc:746-789 (FireWinAccessibilityEvent, GetParentHWND, ::NotifyWinEvent at :789); content/browser/renderer_host/render_widget_host_view_aura.cc:1530-1536 (AccessibilityGetAcceleratedWidget returns legacy HWND); content/browser/renderer_host/legacy_render_widget_host_win.cc:239-240 and render_widget_host_view_aura.cc:3427-3443 (always created); ui/base/win/internal_constants.h:19-20; ui/accessibility/platform/inspect/ax_event_recorder_win.cc:66-90; content/browser/accessibility/ax_inspect_factory_win.cc:74-77 (kAsync when out of process).

3. The document.title nonce cannot serve as a 20 ms clock-alignment marker. On Windows, Chrome explicitly ignores DOCUMENT_TITLE_CHANGED, and a root-node name change is reported only as DOCUMENT_TITLE_CHANGED, so web content produces no WinEvent for a title change. The only WinEvent is the system-generated EVENT_OBJECT_NAMECHANGE (OBJID_WINDOW) on the top-level Chrome_WidgetWin_1, from SetWindowText -> DefWindowProc(WM_SETTEXT). That update goes through BrowserUiController::ScheduleUIUpdate, whose fixed 200 ms PostDelayedTask coalesces title changes. The marker therefore arrives at least about 200 ms late, with jitter of up to one more coalescing window plus timer granularity. Nonces closer than 200 ms apart collapse into one. Separately, all collectors on one host read the same OS clock, so real inter-process skew is on the order of microseconds. The proposed 'offset' would measure pipeline latency, not skew. **[critical]**
   - *Evidence (SOURCE, high confidence):* chromium@52fdf83 ui/accessibility/platform/browser_accessibility_manager_win.cc:732 (DOCUMENT_TITLE_CHANGED in the 'Currently unused events on this platform' list); ui/accessibility/ax_event_generator.cc:567-571 and 931-938 (no NAME_CHANGED for the root; DOCUMENT_TITLE_CHANGED instead); chrome/browser/ui/browser_ui_controller/browser_ui_controller.cc:35 (kUIUpdateCoalescingTime = 200 ms; :33 at tag 154.0.8037.92), :112-170 (PostDelayedTask), :201-204 (UpdateTitleBar); ui/views/win/hwnd_message_handler.cc:1030-1043 (SetWindowText) and :2938-2941 (DefWindowProc WM_SETTEXT).
   - *Implication:* As specified (max skew > 20 ms => INCONCLUSIVE), nearly every segment would be INCONCLUSIVE, which wastes M0/G2 CI round trips. Redefine the rule before M0. Keep the title nonce as a segment-boundary label and record its latency distribution (expect 200 ms or more). Verify the clocks directly instead: every collector stamps GetSystemTimePreciseAsFileTime, and the orchestrator runs a ping/pong over each collector's pipe to bound offsets. If an in-pipeline marker is still wanted, toggle aria-label on a dedicated off-screen role=img element; that yields NAMECHANGE, but with 0-150 ms Blink batching (see the batching finding).
4. Blink batches accessibility serialization, and Chrome fires events in a fixed order. After page load, non-interactive changes (live-region text, name changes, title) are serialized at most once per 150 ms (350 ms before load). Focus, actions, and changes to the focused node are serialized immediately. Inside one batch, the browser fires events in this order: (1) IA2 TEXT_INSERTED/REMOVED, emitted during Unserialize; (2) generated events on ancestors of the focus; (3) EVENT_OBJECT_FOCUS; (4) the remaining generated events, such as LIVEREGIONCHANGED and SHOW; (5) queued UIA TextChanged/AriaProperties events in FinalizeAccessibilityEvents. **[critical]**
   - *Evidence (SOURCE, high confidence):* chromium@52fdf83 third_party/blink/renderer/modules/accessibility/ax_object_cache_impl.cc:3509-3521 (150/350 ms, same at tag 154.0.8037.92 :3515), :3598-3628 (delay between serializations), :5506-5542 and :5602-5630 (immediate-processing criteria); ui/accessibility/platform/browser_accessibility_manager.cc:603-693 (ancestor-of-focus events, then FireFocusEventsIfNeeded, then deferred events, then source events); browser_accessibility_manager_win.cc:1103-1151 (UpdateStep3FireEvents during OnAtomicUpdateFinished) and :1359-1381 (Finalize).
   - *Implication:* K7 (a polite update queued, then an immediate focus move in the same task) reaches B2 as one batch: TEXT_INSERTED(live) -> FOCUS -> LIVEREGIONCHANGED. B2 ordering is a Chrome artefact, not DOM order, and B2 cannot see NVDA's speak/cancel. Build G2 signatures as sets with per-type latency windows: live-region events allow DOM-to-WinEvent delays of 0-150 ms plus IPC; focus is near-immediate. Keep K7 record-only.

Out-of-context WinEvents are queued to the hooking thread, and any cross-process call is served on Chrome's UI thread only after that task ends. Chromium's own recorder reads newText only in-process (kSync, WINEVENT_INCONTEXT). NVDA gets the inserted text because its live-region code runs inside Chrome (nvdaHelperRemote). **[critical]**

Every new Chrome_RenderWidgetHostHWND (a new RenderWidgetHostView, e.g. after a cross-site navigation or in a new tab) has an empty listener map until UIA discovers it. **[critical]**

10. Python 3.12, the default on both runner images (3.12.10), has 15.6 ms time.time() resolution on Windows. The 1 µs GetSystemTimePreciseAsFileTime clock became the default only in Python 3.13 (gh-63207). The WinEvent dwmsEventTime argument is GetTickCount-based milliseconds, so it is also tick-granular. UIA event callbacks carry no timestamp at all. **[critical]**

Either call kernel32.GetSystemTimePreciseAsFileTime through ctypes (and also log QueryPerformanceCounter) at the moment each callback is entered, or use Python 3.13 or later. 11. Threading, message loop and call cost. The thread that calls SetWinEventHook(WINEVENT_OUTOFCONTEXT) must run a GetMessage loop; events are delivered asynchronously but in order. ## timing

The clock-alignment section has the right goal but the wrong mechanism, and as written it will mark many segments INCONCLUSIVE for reasons that have nothing to do with clocks. The document.title pulse does not measure clock offset. It measures Chrome's accessibility pipeline latency. Blink handles title changes, child insertions and text changes on a deferred path: serializations are at least 150 ms apart after page load (350 ms before load), and none is sent while another is still in flight. The top-level window title waits on a fixed 200 ms browser UI coalescing timer. So a pulse that follows a focus change (the end state of K3, K4 and K5) will regularly arrive more than 20 ms late. The premise of a "system precise wall clock" also fails on Windows with the standard APIs. Node's Date.now() and performance.timeOrigin are anchored to GetSystemTimeAsFileTime (about 15.6 ms granularity). Python 3.12's time.time() and time.monotonic() are also 15.6 ms; time.time() became precise only in Python 3.13. Mixing these clocks builds in errors of up to about 16 ms, which uses most of the 20 ms budget. The fix: use QueryPerformanceCounter (QPC) as the single timebase. In Node that is process.hrtime.bigint(), in Python 3.12 time.perf_counter_ns(), in C# Stopwatch.GetTimestamp(), inside NVDA perf_counter_ns(). QPC is consistent across processes on one machine, so native collectors need no offset estimate. The in-page clock (performance.now(), QPC-based, clamped to 100 µs) needs one Cristian-style mapping per document from Node, which should give ±1–2 ms. Keep the title pulse only as a join key and a latency probe; never gate segments on it. Two findings matter most for K7 and interruption timing. First, Chrome reorders events within a batch (focus before other events). Second, neither speech adapter records timestamps: Guidepup reports speech when it is queued, before synthesis, and sees only some cancels. In addition, GitHub Windows runners have no audio device, so NVDA's synth timing (and therefore utterance durations and interruptions) is probably not real-time unless a virtual audio driver is installed. Recommended tolerance: alignment uncertainty ≤0.5 ms between native processes and ≤2 ms for the page, with drift ≤1 ms within a segment; INCONCLUSIVE only when those fail. Pipeline latency is measured and reported, not used as a gate.

### Findings (researcher)

1. The title-pulse 'skew' measures Chrome's deferred accessibility pipeline latency, not clock offset, and that latency is often well over 20 ms. A title change is explicitly non-immediate. Non-immediate updates are serialized at least 150 ms after the previous serialization once load is complete (350 ms before load), never while another serialization is in flight, and only at the next rendering lifecycle (about one frame). Focus, blur and similar events force immediate serialization. **[critical]**

## premises

The K6 premise holds only for live regions that are not alerts. On current Chrome (main @52fdf83b; the key lines are unchanged at the Chrome for Testing stable tag 154.0.8037.92), a region with aria-live=polite, role=status or aria-live=assertive that is inserted already holding text produces only structural events: EVENT_OBJECT_SHOW on the region, REORDER plus IA2 TEXT_INSERTED ('<obj>') on the parent (which is not a live region), and UIA StructureChanged. NVDA builds IA2 live-region speech inside Chrome's process (in-process code), and that code deliberately ignores SHOW on a region root, so nothing is spoken. NV Access maintainers call this by design (nvaccess/nvda#14591). role=alert behaves differently. Chrome fires EVENT_SYSTEM_ALERT plus UIA LiveRegionChanged, and NVDA's event_alert speaks the alert at Spri.NOW. That path ignores the 'Report dynamic content changes' setting, and the text it reads differs between NVDA 2026.2 and the 2026.3 beta. So K6 must be split, and the alert variant should be expected to be ANNOUNCED. Where announcement is decided is the Blink accessibility snapshot, not the JS task. Chrome sends ordinary changes to the screen reader in batches, at most once per 150 ms after page load; focus changes and user actions are sent at once. So 'insert empty region, then fill it' is silent whenever both steps land in the same batch. For K7, NVDA does not cancel speech on a focus change. The polite text (NORMAL priority) is queued ahead of the focus speech, because Chrome fires TEXT_INSERTED before FOCUS within one update. Expected result: polite text, then the focused control, with no cancel. The exception is focus moving from browse mode into a control that switches NVDA to focus mode (or say-all running): cancelSpeech then drops the polite text or cuts it off. Neither candidate adapter can tell spoken text from text that was queued and then cancelled. The cross-cutting problems I found change the M0 setup and the G1/G2 definitions. B2's hook set misses EVENT_SYSTEM_ALERT and EVENT_SYSTEM_FOREGROUND. If NVDA falls back to UIA for Chrome, K1 would likely be silent. Chrome's batching makes the document.title nonce useless as a 20 ms alignment marker. Python 3.12's time.time() uses the coarse Windows clock. The runner needs a real audio device. Before M3, the owner should pre-register a decision rule for K6 and prune the regression catalogue on that basis.

### Findings (researcher)

1. K6 polite/status/assertive (not alert): when a live region is inserted already holding text, Chrome on Windows fires only structural events: EVENT_OBJECT_SHOW on the new region root, and EVENT_OBJECT_REORDER plus IA2_EVENT_TEXT_INSERTED (embedded-object char) on its parent, which is not a live region; UIA gets StructureChanged ChildAdded/ChildrenReordered only. It fires no EVENT_OBJECT_LIVEREGIONCHANGED, no UIA LiveRegionChanged and no TEXT_INSERTED on the region itself. **[critical]**
   - *Evidence (SOURCE, high confidence):* chromium/chromium@52fdf83b:ui/accessibility/ax_event_generator.cc:1078-1083 (a created node gets ALERT, else LIVE_REGION_CREATED if it is an active live root) and :1362-1367 (a node with ALERT or LIVE_REGION_CREATED has LIVE_REGION_CHANGED removed). ui/accessibility/platform/browser_accessibility_manager_win.cc:688-690 (SUBTREE_CREATED maps to EVENT_OBJECT_SHOW and UIA ChildAdded) and :721-746 (LIVE_REGION_CREATED and LIVE_REGION_NODE_CHANGED are listed as 'Currently unused events on this platform'). ui/accessibility/platform/browser_accessibility_com_win.cc:1779 ('The rest of the events only fire on changes, not on new objects') and :1802-1816 (TEXT_INSERTED only for existing nodes). Chromium's own Windows dump test content/test/data/accessibility/event/live-region-create-expected-win.txt gives REORDER on the container, SHOW on the div, and TEXT_INSERTED '<obj>' on the container; the UIA expectation is StructureChanged only. Same logic at tag 154.0.8037.92 (manager_win.cc:395,734; ax_event_generator.cc:1040,1323). role=status gets implicit polite from blink ax_object.cc:5852-5882.
   - *Implication:* The flagship premise is grounded on the IA2 path for polite and status. Use these exact signatures in G2: SHOW on the region root, REORDER and TEXT_INSERTED on the parent, and none of LIVEREGIONCHANGED, UIA LiveRegionChanged, or TEXT_INSERTED on a live node. The DOM timeline's 'inserted already non-empty' flag should map one-to-one onto this signature.
2. For Chrome, NVDA generates live-region speech in-process (nvdaHelperRemote's WinEvent hook inside chrome.exe). It reacts only to NAMECHANGE, DESCRIPTIONCHANGE, SHOW, IA2 TEXT_UPDATED and TEXT_INSERTED on nodes whose container-live is polite or assertive, and it explicitly ignores SHOW on the root of a region. Combined with the previous finding, a polite or status region inserted with content is never spoken. NV Access maintainers have stated this is by design. **[critical]**
   - *Evidence (SOURCE, high confidence):* nvaccess/nvda@1406f9f8 (master; file unchanged at release-2026.2 f62c9805):nvdaHelper/remote/ia2LiveRegions.cpp. Lines 110-123 limit the event filter and require Chrome to be the foreground window; 147-150 check container-live; 171-175 drop busy regions; 194-226 ignore SHOW on a root ('we assume we are the root of the region and therefore should ignore the event'); 254-258 report text over RPC. source/NVDAHelper/__init__.py:287-319 is gated by reportDynamicContentChanges and queues speakText at Spri.NEXT for assertive, NORMAL for polite. Issue https://github.com/nvaccess/nvda/issues/14591 ('role=status live region not announced when injected into DOM', closed not_planned 2024-03-19). Comments there: michaelDCurran (2023-01-30) says ATs should speak updates, not the initial value; jcsteh (2023-10-29) separates updates from content present when the region is created. Practitioner tests agree: TetraLogical 2024-05-01 (NVDA+Chrome: pre-populated status and polite regions not announced) and Scott O'Hara 'Are we live?' (2022).
   - *Implication:* Expect K6a (polite), K6b (role=status) and K6c (aria-live=assertive) to be NOT announced, about 0 of 50, on NVDA 2026.2 or 2026.3 with IA2. Because maintainers stated it is intended, the premise is unlikely to drift within a release, but pin and record the NVDA build.
3. K6 role=alert inserted with content IS announced. When a role=alert or role=alertdialog node is created or unhidden, Chrome fires EVENT_SYSTEM_ALERT and UIA LiveRegionChanged. NVDA's IAccessible.event_alert speaks role=alert at Spri.NOW, which interrupts current speech and resumes it afterwards. That path ignores 'Report dynamic content changes'. It does nothing if focus is inside the alert, and it ignores alertdialog because NVDA gives that object role DIALOG. What gets read differs by version: 2026.2 reads only plain-text and paragraph-level content (through the Dialog description) plus focusable children; 2026.3 also reads headings, lists and list items. **[critical]**
   - *Evidence (SOURCE, high confidence):* chromium@52fdf83b:browser_accessibility_manager_win.cc:394-400 (ALERT maps to EVENT_SYSTEM_ALERT and UIA_LiveRegionChangedEventId); ui/accessibility/ax_role_properties.cc:58-66 (IsAlert covers kAlert and kAlertDialog). Chromium test add-alert-expected-win.txt shows EVENT_SYSTEM_ALERT for both alert and alertdialog. nvda@1406f9f8:source/NVDAObjects/IAccessible/__init__.py:2025-2066 (event_alert: role check, focus-ancestor skip, speakObject(..., Spri.NOW)); ia2Web.py:497-498 (web alerts get the Dialog overlay); behaviors.py:89-129 (Dialog.getDialogText). Commit 62ab86728 (#20056, fixes #14990) is in release-2026.3beta3 but not release-2026.2. Practitioner reports: #14591's reporter says the injected alert was announced; TetraLogical says NVDA+Chrome announces pre-populated role=alert 'inconsistently'.
   - *Implication:* Split K6. K6d (role=alert) must be expected ANNOUNCED, through the alert channel at NOW priority. Any regression mechanism that treats an inserted alert as silent loses its premise. A mechanism that keeps a strong premise: downgrading a conditionally rendered toast from role=alert to role=status. axe accepts both and the AX tree shows only a role change, but NVDA goes from announced to silent. Pin the NVDA version, because K6d's spoken text changes with 2026.3.
4. The B2 hook set as specified (EVENT_OBJECT_* plus the IA2 ranges) cannot see EVENT_SYSTEM_ALERT (0x0002), the only IA2-side signal for an inserted alert. It also misses two other events the experiment needs. EVENT_SYSTEM_FOREGROUND matters because NVDA's in-process live-region hook drops every event unless Chrome is the foreground window. EVENT_OBJECT_DESCRIPTIONCHANGE is one of the events NVDA's live-region hook acts on. **[critical]**
   - *Evidence (SOURCE, high confidence):* nvda@1406f9f8:source/winUser.py:355 (EVENT_SYSTEM_ALERT=0x2); IAccessibleHandler/internalWinEventHandler.py:37 maps it to 'alert'; nvdaHelper/remote/ia2LiveRegions.cpp:110-123 (foreground check and accepted event list). The project brief's B2 list names FOCUS, NAMECHANGE, LIVEREGIONCHANGED, SHOW, HIDE, REORDER and IA2 text insert/remove only.
   - *Implication:* Add a second SetWinEventHook range covering EVENT_SYSTEM_ALERT and EVENT_SYSTEM_FOREGROUND (or hook EVENT_SYSTEM_* entirely), plus DESCRIPTIONCHANGE. Without this, G2 cannot define a signature for K6d or for alert regressions, and a lost foreground cannot be detected as the cause of silence.
5. Blink batches accessibility snapshots sent to the screen reader. Ordinary changes are sent at most once per 150 ms after load (350 ms before load completes): child insertion, text changes, live-region events and document title changes. Focus changes, AX actions and changes to the focused node are sent at once. Within one update on Windows, IA2 TEXT_INSERTED/REMOVED fire during OnAtomicUpdateFinished, before EVENT_OBJECT_FOCUS. Generated events on the focus's ancestors fire before the focus event; all other generated events (LIVEREGIONCHANGED, SHOW, EVENT_SYSTEM_ALERT) fire after it. **[critical]**
   - *Evidence (SOURCE, high confidence):* chromium@52fdf83b:third_party/blink/renderer/modules/accessibility/ax_object_cache_impl.cc:3509-3521 (kDelayForDeferredUpdatesAfterPageLoad=150, BeforePageLoad=350; also 150 at tag 154.0.8037.92 line 3515), :3605-3628 (waits delay minus elapsed since last snapshot), :5506-5545 (immediate: action, focused target, kFocus/kBlur/kClicked; kDocumentTitleChanged is not immediate), :5602-5650 (kChildInserted and text changes return false, i.e. batched). ui/accessibility/platform/browser_accessibility_manager_win.cc:1103-1153 (IA2 text events in OnAtomicUpdateFinished). browser_accessibility_manager.cc:616-680 (ancestor events, then FireFocusEventsIfNeeded, then deferred events).
   - *Implication:* (a) 'Insert empty region, then fill it' is silent if both steps land in one snapshot: the same task, the same frame, or within about 150 ms of the previous snapshot. Add K6e, a fill-delay sweep (0, rAF, 50, 100, 150, 250, 500 ms), to measure this. (b) In K7, the live update and the focus move almost always share one snapshot, regardless of JS order. (c) The document.title nonce reaches the WinEvent stream 0 to 150 ms plus one frame after the DOM change, by a variable amount, so it cannot support a 20 ms skew rule. Measure that latency rather than treating it as clock skew, or use an event that is sent at once. (d) INFERENCE: NVDA browse-mode activation calls doAction (browseMode.py:687-699), which arrives in Chrome as an AX action and is sent at once; a focus-mode keypress is batched. The mode can therefore change which snapshot a canary's mutation lands in.
6. K7: NVDA does not cancel speech on a focus change in general. The live-region text is queued at Spri.NORMAL (polite) or Spri.NEXT (assertive) before the focus speech, which is also NORMAL, so with the default settings the polite text is spoken first and the focused control second, with no cancel. Speech is cancelled only in these cases: browse mode switching to focus mode because focus landed on an auto-focus-mode control such as an edit field, say-all running, or a foreground window change. Removal of expired focus speech affects only speech generated by focus events, never live-region speech. **[critical]**
   - *Evidence (SOURCE, high confidence):* nvda@1406f9f8:source/NVDAObjects/__init__.py:1365-1373 (event_gainFocus does not cancel) and :1382-1387 (event_foreground does cancelSpeech); source/browseMode.py:2299-2308 (cancelSpeech only when not oldPassThrough and (passThrough or sayAll running)). Same logic at release-2026.2, browseMode.py:2215-2217. source/eventHandler.py:186-309 (FocusLossCancellableSpeechCommand, only for OutputReason.FOCUS); source/speech/priorities.py:12-27; source/speech/manager.py:282-290 (only the first NOW item interrupts); source/config/configSpec.py:220 (autoPassThroughOnFocusChange=true) and :371 (cancelExpiredFocusSpeech default 0, i.e. enabled). Issue #3777 (2015) removed the unconditional browse-mode cancel.

## playwright

Playwright can do the page-state job, but six of its behaviours undermine the experiment unless the harness works around them on purpose. (1) For every launched page, Playwright 1.63 turns on CDP focus emulation (Emulation.setFocusEmulationEnabled), and there is no launch option to turn it off. As a result, document.hasFocus(), focus/focusin events and visibilityState all report "focused" even when Chrome is not the OS foreground window. Meanwhile Chrome withholds native EVENT_OBJECT_FOCUS until its window has focus. The handover check therefore has to use Win32 and accessibility-level focus, never DOM signals, and DOM focusin cannot stand in for platform focus. (2) Chrome holds back updates to the top-level window title for 200 ms (kUIUpdateCoalescingTime), so a title nonce read from the window caption will routinely break the 20 ms skew rule. The nonce has to be read from the document object's NAMECHANGE/UIA Name channel. Because every collector reads the same OS clock, what the nonce mostly measures is pipeline latency, not clock skew. (3) Defaults for non-persistent chromium.launch(): a fresh temp profile per run, --no-startup-window, no --enable-automation since v1.60, background throttling disabled, and --no-sandbox unless chromiumSandbox:true. Chrome for Testing honours --disable-infobars, so no infobar should appear and speak. (4) Use the exact tested pair: Playwright 1.63.0 ships CfT 153.0.8010.12 for win64. CfT Stable is now 154.0.8037.92, and Playwright 1.64 (Chromium 155) is not out yet. (5) For Arm B: page.accessibility was removed in v1.57. ariaSnapshot is Playwright's own JavaScript role/name computation and has no live-region properties. Only CDP Accessibility.getFullAXTree shows Chrome's real tree with live/atomic/relevant/busy. Also, @axe-core/playwright analyze() opens a new tab via context.newPage(), which in headed Chrome steals focus. (6) addInitScript runs before page scripts in every frame, including out-of-process iframes. The MutationObserver still needs an attachShadow patch, takeRecords() to keep event order, and a K6 classifier that allows for Chrome batching accessibility updates once per frame. 'Same mutation batch' is the wrong boundary for K6. The rule against CDP input during AT segments can be enforced fail-closed through Playwright's client instrumentation hook, and then audited from a DEBUG=pw:protocol log that is scanned for Input.* calls. 1. Playwright always enables CDP focus emulation on the main frame of every page it launches, in both headed and headless mode. The only documented way out is connectOverCDP({noDefaults:true}) on the default context (since v1.60). With emulation on, Blink's FocusController reports IsFocused() and IsActive() as true. So document.hasFocus() is always true, and focus/focusin events fire on element.focus() even when Chrome is not the OS foreground window. The browser side also bumps the capturer count, so the page stays 'visible'. Chrome's native accessibility layer, however, fires EVENT_OBJECT_FOCUS only when its RenderWidgetHostView has focus. When the window later gains focus, it fires one focus event for whatever is focused at that moment. page.bringToFront() calls WebContents::Activate()+Focus(), but on Windows that is a plain SetForegroundWindow, which the foreground lock can block. **[critical]**
   - *Evidence (SOURCE, high confidence):* microsoft/playwright@1b025d7 (v1.63.0):packages/playwright-core/src/server/chromium/crPage.ts:542-548 (Emulation.setFocusEmulationEnabled {enabled:true} unless noDefaults on default context); docs/src/api/class-browsertype.md:231-239 (noDefaults, since v1.60, 'focus emulation is not enabled'); chromium/src@154.0.8037.92:third_party/blink/renderer/core/page/focus_controller.h:122,125 (IsActive/IsFocused OR is_emulating_focus_); content/browser/devtools/protocol/emulation_handler.cc:1014-1027 (IncrementCapturerCount stay_hidden=false); ui/accessibility/platform/browser_accessibility_manager.cc:232-238 ('Don't fire focus events if the window itself doesn't have focus') and :436-444 (OnWindowFocused -> FireFocusEventsIfNeeded); content/browser/devtools/protocol/page_handler.cc:1754-1770 (BringToFront = Activate + Focus); ui/views/win/hwnd_message_handler.cc:884-896 (Activate = SetWindowPos + ::SetForegroundWindow)
   - *Implication:* Handover verification must not use document.hasFocus(), focus events or visibilityState. Check (a) GetForegroundWindow() == the Chrome top-level HWND, and (b) the UIA focused element or the last B2 EVENT_OBJECT_FOCUS resolves to the declared anchor inside the document, plus NVDA's focus object via the adapter. 2. Chrome waits 200 ms before applying window-title updates (BrowserUiController kUIUpdateCoalescingTime). **Missed by the researcher:**

- CRITICAL, clock alignment: the title-nonce design cannot meet a 20 ms skew rule on any Windows channel. The researcher's fix (read the document object's NAMECHANGE/UIA Name) relies on an event Chrome never fires: ax_event_generator.cc:568-572 suppresses NAME_CHANGED on the tree root, and DOCUMENT_TITLE_CHANGED is unused on Windows (browser_accessibility_manager_win.cc:732 @154 / :730 @153). The only platform signal left is the browser HWND caption, coalesced up to 200 ms (browser_ui_controller.cc:33,160-169). All collectors read the same OS clock, so 'skew' is really pipeline latency, and that latency is variable by design. Proposed change: gate on direct inter-process clock agreement (each collector logs paired GetSystemTimePreciseAsFileTime/QPC samples at segment boundaries via a local ping), and record title-nonce latency only as a diagnostic. If an accessibility-observable nonce is needed, use a non-title change (e.g. aria-label on an off-screen, non-focused element) emitted after at least 150 ms of accessibility quiet (350 ms before load completes). Cheapest test: in one M0 job without NVDA, run 200 title toggles and 200 aria-label toggles, then histogram DOM-to-WinEvent latency for both. Expected: caption 0-200 ms, no document-object event, element NAMECHANGE between about 1 frame and 150 ms. (SOURCE)
- CRITICAL, Blink serialization throttle: Blink accessibility serialization is throttled to one every 150 ms after load completes (350 ms during load) unless something forces it: focus change, an accessibility action, or a change on the focused element (ax_object_cache_impl.cc:3507-3519, 3594-3620, 5524-5564; same constants in 153.0.8010.12 at :3498/:3503). Effects: (a) K1/K2 platform events carry 0-150 ms of jitter. (b) For K6, a region inserted empty and filled within the remaining throttle window coalesces into one update. It then emits LIVE_REGION_CREATED (unused on Windows), and LIVE_REGION_CHANGED is removed (ax_event_generator.cc:1037-1042, 1320-1325), so it is indistinguishable from 'inserted non-empty'. K6 variants need fill delays above 150 ms (above 350 ms before load completes) to be deterministic. Each record should store document load-complete state and the time since the last focus change. (c) Prediction from source: the B2 signature for K6 is EVENT_OBJECT_SHOW + UIA StructureChanged(ChildAdded), with no EVENT_OBJECT_LIVEREGIONCHANGED or UIA LiveRegionChanged (browser_accessibility_manager_win.cc:688-691). (SOURCE)
- CRITICAL, K7 ordering: platform event order inside one serialization batch is fixed by Chrome, not by DOM order. BrowserAccessibilityManager::OnAccessibilityEvents first fires generated events on ancestors of the focused node, then the FOCUS event, then all other generated events; Windows fires IA2 text-changed events in FinalizeAccessibilityEvents (browser_accessibility_manager.cc:615-690 @154; :666/:669 @153). A focus move forces immediate serialization (TreeUpdateReason::kNodeGainedFocus, ax_object_cache_impl.cc:5562), which flushes a pending polite update into the same batch. So in K7 (polite update, then an immediate focus move) B2 will typically see EVENT_OBJECT_FOCUS before EVENT_OBJECT_LIVEREGIONCHANGED, the reverse of DOM order. The speak/cancel analysis must group events by serialization batch rather than use DOM timeline order. (SOURCE)
- K2 B2 signature: updating the text of an existing role=alert node produces LIVE_REGION_CHANGED, i.e. EVENT_OBJECT_LIVEREGIONCHANGED + UIA LiveRegionChanged, not EVENT_SYSTEM_ALERT. ALERT is generated only when the alert node is created, changes role to alert, or becomes unignored (ax_event_generator.cc:394, 417, 1037-1038). If G2 expects EVENT_SYSTEM_ALERT for 'role=alert update', K2 will fail by construction. Either define K2 as alert insertion or expect LIVEREGIONCHANGED. (SOURCE)
- K5 B2 signature: a document.title update on a pushState route change gives no document-level WinEvent or UIA event on Windows (see above). Only the browser HWND caption NAMECHANGE arrives, up to 200 ms later. The K5 signature should rely on EVENT_OBJECT_FOCUS/UIA focus on the h1 and treat the caption change as optional and delayed. (SOURCE)
- Focus emulation can probably be turned off at runtime without connectOverCDP. Blink's InspectorEmulationAgent::setFocusEmulationEnabled writes the shared Page FocusController, and the browser-side handler falls through to the renderer in both branches (inspector_emulation_agent.cc:603-613 @153.0.8010.12; emulation_handler.cc:1014-1027). So Emulation.setFocusEmulationEnabled({enabled:false}) from context.newCDPSession(page) should clear renderer-side emulation while Playwright's capturer handle keeps the page visible. Playwright's session state restores emulation in a new renderer (inspector_emulation_agent.cc:262-263), so the call would have to be repeated after every cross-process navigation. Cheap test: with Notepad in front, check document.hasFocus() and whether element.focus() fires focusin, before and after the call. (INFERENCE from SOURCE)

### Open questions

- Does Chrome 153 on Windows reliably fire EVENT_OBJECT_NAMECHANGE and a UIA Name change on the document object when document.title changes, and with what latency distribution? Cheapest test: 200 title toggles with the B2 listener running, NVDA absent.
- Does NVDA (pinned version) speak, or cancel speech on, document.title or window-caption changes in Chrome browse mode? This decides where the nonce may be emitted safely.
- On GitHub-hosted windows-2022/2025, can a background process (node or python) reliably foreground the Chrome window through page.bringToFront() / SetForegroundWindow, or does the foreground lock force a different OS-level technique? Note that an Alt-key SendInput trick would be heard by NVDA and may focus Chrome's menu button.
- What is the default display resolution on the current windows-2022 and windows-2025 images, and does Set-DisplayResolution work there?
- Does turning off focus emulation (connectOverCDP({noDefaults:true}) on a self-launched CfT) change any K1-K7 outcome once the handover is verified? If not, keep Playwright's defaults.
- Does locking the AX mode (--force-renderer-accessibility=screen-reader) change NVDA's behaviour or the choice between IA2 and UIA, compared with the bare flag?
- What window caption does Chrome give windows from DevTools-created (off-the-record) browser contexts, and does NVDA's announcement on foreground include anything the speech matcher must normalise?
